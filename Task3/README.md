# Задание 3. Разработка проверочного листа по безопасности данных

### Сформируйте список требований, которым должны удовлетворить внешние интеграции

**A. Требования к безопасности:**

1.  **Шифрование канала:** Все взаимодействия между `tenant-core-app` и `partner_platform` (API вызовы, Webhook) должны осуществляться исключительно по протоколу HTTPS с использованием актуальных версий TLS (не ниже 1.2) и надежных шифронаборов.
2.  **Аутентификация систем:**
    *   **PropDev -> Partner:** Система PropDevelopment (`tenant-core-app`) должна аутентифицироваться на API Платформы Партнера с использованием надежного метода (см. раздел B). Статические, не сменяемые токены недопустимы.
    *   **Partner -> PropDev:** Платформа Партнера должна аутентифицироваться при вызове Webhook эндпоинта PropDevelopment. Это можно реализовать через проверку подписи запроса (например, HMAC с общим секретом) или требование специального токена в заголовке.
3.  **Авторизация систем:** API-ключ или токен, используемый `tenant-core-app` для доступа к API партнера, должен иметь минимально необходимые права (например, управлять только теми устройствами, которые относятся к ЖК PropDevelopment, синхронизировать данные жильцов и т.д.). Аналогично, если партнер вызывает API PropDev, его права должны быть ограничены.
4.  **Минимизация передаваемых данных:** Передавать партнеру следует только минимально необходимый объем данных для функционирования сервиса. Избегать передачи избыточных ПДн собственников. Вместо ФИО использовать внутренние идентификаторы.
5.  **Безопасность ПДн и Биометрии:**
    *   Партнер должен гарантировать соответствие требованиям законодательства РФ (152-ФЗ, включая требования к обработке биометрических ПДн) при сборе, обработке и хранении данных (фото лиц, номера машин). Это должно быть закреплено в договоре.
    *   PropDevelopment *не должен* хранить у себя необезличенные биометрические данные (фото лиц), полученные от партнера. Регистрация биометрии должна выполняться в системе партнера с согласия пользователя.
    *   Номера машин могут храниться в PropDevelopment и передаваться партнеру вместе с разрешением на доступ.
6.  **Защита от атак:** API эндпоинты и Webhook URL должны быть защищены от распространенных атак (валидация ввода, защита от CSRF для веб-интерфейсов управления, если они есть, защита от DoS/Bruteforce через rate limiting).
7.  **Управление секретами:** API-ключи, секреты для подписи Webhook и другие учетные данные для взаимодействия систем должны храниться безопасно (не в коде, не в системе контроля версий) с использованием специализированных решений (Vault, KMS облачного провайдера, переменные окружения) и подлежать регулярной ротации.
8.  **Аудит и Логирование:** Все запросы к API партнера и все входящие Webhook запросы должны подробно логироваться на стороне PropDevelopment (время, источник, результат, основные параметры). Партнер также должен обеспечить логирование со своей стороны.

**B. Протоколы аутентификации и авторизации:**

1.  **Аутентификация пользователя:** Собственник аутентифицируется в мобильном приложении PropDevelopment с помощью `auth-service-1` (Keycloak) по протоколу OAuth 2.0 / OpenID Connect. Полученный токен используется для авторизации запросов от мобильного приложения к `tenant-core-app`.
2.  **Аутентификация системы PropDev на API Партнера:**
    *   **Рекомендуемый:** OAuth 2.0 Client Credentials Grant. `tenant-core-app` получает токен доступа от сервера авторизации партнера, используя свой client_id и client_secret, и передает этот токен при каждом вызове API партнера. Требует наличия сервера авторизации у партнера.
    *   **Допустимый (при строгом контроле):** Статический API Key, передаваемый в заголовке запроса. Требует безопасного хранения, обязательной регулярной ротации ключа и мониторинга его использования.
3.  **Аутентификация системы Партнера при вызове Webhook PropDev:**
    *   **Рекомендуемый:** Проверка цифровой подписи запроса. Партнер подписывает тело Webhook запроса с использованием заранее согласованного секрета (например, HMAC-SHA256) и передает подпись в заголовке. `tenant-core-app` проверяет подпись перед обработкой запроса.
    *   **Альтернатива:** Требование наличия статического токена (секрета) в заголовке входящего Webhook запроса от партнера. Менее надежно, чем подпись.
4.  **Авторизация запросов:**
    *   `tenant-core-app` перед отправкой команды партнеру проверяет права аутентифицированного пользователя (собственника) на выполнение этого действия (например, право открыть шлагбаум конкретного паркинга) на основе данных в `tenant-core-db`.
    *   API Партнера должен проверять, что аутентифицированная система (`tenant-core-app`) имеет право управлять конкретным устройством, указанным в запросе.

**C. Организация взаимодействия:**

1.  **Стиль API:** Предпочтительно использовать RESTful API с передачей данных в формате JSON.
2.  **Синхронизация данных о жильцах/правах:**
    *   `tenant-core-app` отвечает за ведение актуального списка собственников и их прав доступа к устройствам Умного Дома (какие домофоны/шлагбаумы им доступны).
    *   При изменении данных (добавление/удаление жильца, изменение прав, добавление/удаление номера машины) `tenant-core-app` должен вызывать соответствующий API-метод Платформы Партнера для обновления данных на стороне партнера (Push-модель).
    *   Необходим механизм первоначальной загрузки и периодической сверки данных для обеспечения консистентности.
3.  **Выполнение команд управления:**
    *   Запросы на открытие домофона/шлагбаума инициируются из `mobile_app` к `tenant-core-app`.
    *   `tenant-core-app` после проверки прав вызывает соответствующий API-метод Платформы Партнера, передавая идентификатор устройства и, возможно, идентификатор пользователя.
    *   API Партнера должно быть идемпотентным, где это возможно. Ответ API должен содержать статус операции (успешно отправлена команда / ошибка).
4.  **Получение событий:**
    *   Платформа Партнера при наступлении событий (доступ по лицу/номеру, звонок, ошибка устройства) отправляет асинхронные уведомления на заранее сконфигурированный Webhook URL в `tenant-core-app`.
    *   Формат сообщений Webhook должен быть четко специфицирован (JSON). Сообщения должны содержать тип события, идентификатор устройства, временную метку, идентификатор пользователя (если применимо) и другую релевантную информацию.
    *   `tenant-core-app` должен быстро подтверждать получение Webhook (например, HTTP 200 OK) и обрабатывать его асинхронно, чтобы не блокировать партнера.
5.  **Обработка ошибок:** Должны быть четко определены коды HTTP-статусов и форматы сообщений об ошибках для API и Webhooks. Необходимо предусмотреть логику повторных попыток для временных сетевых ошибок или недоступности сервисов (с использованием exponential backoff).
6.  **Мониторинг:** Необходимо настроить мониторинг доступности API Партнера и работоспособности обработки входящих Webhooks. Отслеживать количество ошибок и задержки ответов.

Этот подход позволит интегрировать новые сервисы, сохранив контроль над данными пользователей и правами доступа в системе PropDevelopment, и обеспечит необходимый уровень безопасности взаимодействия.
